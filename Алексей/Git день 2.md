**Git Merge и Rebase** — два основных способа объединить изменения из одной ветки в другую.

### 1. Git Merge (слияние)

**Что делает:**  
Берёт изменения из одной ветки и вливает их в текущую. История обеих веток полностью сохраняется.

#### Виды merge

**Fast-forward** (быстрый вперёд)  
Если в целевой ветке не было новых коммитов, Git просто передвигает указатель ветки вперёд. Новый коммит **не создаётся**.

```
До:
main:    A---B
feature:     \---C---D

После git merge feature:
main:    A---B---C---D
```

**Обычный (трёхсторонний) merge**  
Если обе ветки разошлись, Git создаёт специальный **merge-коммит**, у которого два родителя.

```
До:
main:    A---B---E
feature:     \---C---D

После git merge feature:
main:    A---B---E---M
              \---C---D/
```

#### Основные команды

```bash
git switch main
git merge feature          # слить feature в main
git merge --no-ff feature  # всегда создавать merge-коммит (даже если возможен fast-forward)
```

#### Плюсы merge
- Безопасно — история не переписывается.
- Хорошо видно, когда и какие ветки сливались.
- Подходит для публичных/общих веток.

#### Минусы
- История становится «запутанной» (много merge-коммитов).
- `git log --graph` выглядит как паутина.

---

### 2. Git Rebase (перебазирование)

**Что делает:**  
Берёт коммиты одной ветки и **последовательно накладывает** их поверх другой ветки. История становится линейной.

```
До:
main:    A---B---E
feature:     \---C---D

После git rebase main (находясь в feature):
main:    A---B---E
feature:         \---C'---D'
```

Коммиты C и D получают новые хеши (C' и D') — это уже **другие** коммиты.

#### Основные команды

```bash
# Классический вариант: перебазировать feature на актуальный main
git switch feature
git rebase main

# Интерактивный rebase (очень мощный инструмент)
git rebase -i HEAD~3          # отредактировать последние 3 коммита
git rebase -i main            # перебазировать на main с возможностью править коммиты
```

В интерактивном режиме можно:
- менять порядок коммитов
- объединять (`squash` / `fixup`)
- переписывать сообщения
- удалять коммиты
- останавливаться и править код (`edit`)

#### Плюсы rebase
- Чистая, линейная история.
- Легче читать `git log`.
- Удобно «подчищать» свою ветку перед слиянием.

#### Минусы и опасности
- **Переписывает историю**. Если ветку уже запушили и другие люди с ней работают — будет боль.
- При конфликтах их приходится решать **последовательно** (по одному коммиту).
- Легко потерять коммиты, если неаккуратно.

---

### 3. Сравнение: когда что использовать

| Ситуация                              | Лучше использовать | Почему |
|---------------------------------------|--------------------|--------|
| Сливаешь свою feature-ветку в `main`  | **Rebase** + merge | Чистая история |
| Сливаешь `main` в свою долгую feature | **Rebase**         | Актуализировать ветку |
| Общая ветка, над которой работают несколько людей | **Merge**     | Не переписывать общую историю |
| Хочешь сохранить точную хронологию    | **Merge**          | Все развилки остаются |
| Хочешь красивый линейный `git log`    | **Rebase**         | История выглядит как прямая линия |
| Уже запушил ветку и кто-то её использует | **Merge**       | Безопаснее |

---

### 4. Золотые правила

1. **Никогда не делай rebase публичных веток** (`main`, `develop` и т.п.), если на них уже кто-то работает.
2. **Можно и нужно** делать rebase своей личной feature-ветки сколько угодно раз.
3. Перед тем как делать `git push` после rebase используй:
   ```bash
   git push --force-with-lease
   ```
   (безопаснее, чем обычный `--force`).
4. Если боишься — всегда можно сделать резервную ветку перед rebase:
   ```bash
   git branch feature-backup
   ```

---

### 5. Практический сценарий «как делают чаще всего»

```bash
# 1. Создали feature-ветку и поработали
git switch -c feature/login
# ... коммиты ...

# 2. Пока ты работал, в main появились новые коммиты
git fetch origin
git rebase origin/main          # переносим свои коммиты поверх свежего main

# 3. Если были конфликты — решаем, потом:
git add .
git rebase --continue

# 4. Отправляем ветку
git push --force-with-lease

# 5. На GitHub/GitLab создаём Pull Request
# После ревью вливаем через "Rebase and merge" или "Squash and merge"
```

---

**Краткий итог:**

- **Merge** — «сохранить всю историю как было».
- **Rebase** — «переписать историю так, будто я начал работу позже».

Для обучения лучше сначала хорошо освоить **merge**, а потом переходить к **rebase**.
