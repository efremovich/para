# Описание проекта fuel-app-backend

## 1. Общая информация

**Название проекта:** fuel-app-backend  
**Язык программирования:** Go 1.24.6  
**Назначение:** Backend API для мобильного приложения работы с топливными картами  
**Модуль Go:** `git.autocard-yug.ru/backend/fuel-backend-app`  
**Сервис:** Backend-приложение для управления топливными картами, компаниями, пользователями, транзакциями и связанными сущностями

## 2. Архитектура

Проект построен на принципах **Clean Architecture** с четким разделением на слои:

### Слои архитектуры:

1. **Controller** (`internal/controller/`) - HTTP/gRPC контроллеры, обработка запросов
2. **Usecase** (`internal/usecase/`) - бизнес-логика приложения
3. **Repository** (`internal/repository/`) - работа с базой данных
4. **Entity** (`internal/entity/`) - доменные сущности

### Паттерны:

- **gRPC + HTTP Gateway** - используется grpc-gateway для автоматической генерации HTTP REST API из gRPC сервисов
- **Микросервисная архитектура** - интеграция с другими сервисами через RabbitMQ
- **Dependency Injection** - зависимости передаются через конструкторы
- **Repository Pattern** - абстракция доступа к данным

### Архитектурная схема:

```
┌─────────────────┐
│   HTTP Client   │
└────────┬────────┘
         │ HTTP REST
         ▼
┌─────────────────┐     ┌─────────────────┐
│  HTTP Gateway   │────▶│  gRPC Server    │
│  (grpc-gateway) │     │                 │
└─────────────────┘     └────────┬────────┘
                                 │
                                 ▼
                    ┌──────────────────────┐
                    │   Controller Layer   │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │    Usecase Layer     │
                    │   (Business Logic)   │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │  Repository Layer    │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │   PostgreSQL DB     │
                    └──────────────────────┘
```

## 3. Технологический стек

### Backend
- **Язык:** Go 1.24.6
- **Фреймворк:** Стандартная библиотека Go + Fiber (для HTTP middleware)

### База данных
- **СУБД:** PostgreSQL 15.4
- **Драйвер:** `github.com/jmoiron/sqlx` + `github.com/lib/pq`
- **Query Builder:** `github.com/Masterminds/squirrel`

### API
- **gRPC:** `google.golang.org/grpc`
- **HTTP Gateway:** `github.com/grpc-ecosystem/grpc-gateway/v2`
- **Protocol Buffers:** `google.golang.org/protobuf`

### Брокер сообщений
- **RabbitMQ:** 3-management-alpine
- Используется для асинхронной обработки сообщений и интеграции с другими сервисами

### Мониторинг и трейсинг
- **Трейсинг:** OpenTelemetry (`go.opentelemetry.io/otel`)
- **Метрики:** Prometheus (`github.com/prometheus/client_golang`)
- **Логирование:** `git.autocard-yug.ru/utils/alogger/v2`

### Хранилище файлов
- **MinIO/S3:** Опциональное хранилище файлов через `github.com/minio/minio-go/v7`
- Поддерживается как MinIO, так и AWS S3

### Контейнеризация
- **Docker:** Контейнеризация приложения
- **Docker Compose:** Локальная разработка и тестирование

### Утилиты
- **Конфигурация:** `git.autocard-yug.ru/utils/aconf/v3`
- **База данных:** `git.autocard-yug.ru/utils/postgresdb`
- **Трейсинг:** `git.autocard-yug.ru/utils/atracer`
- **Метрики:** `git.autocard-yug.ru/utils/ametrics`

- `TransactionService` - транзакции
- `ContactService` - контакты
- `ContractService` - договоры

Swagger документация доступна по адресу: `/swagger/`

### Метрики

- **Endpoint:** `/metrics`
- **Метод:** GET

## 7. Конфигурация

### Переменные окружения

Конфигурация приложения загружается через библиотеку `aconf` из переменных окружения.

#### Основные настройки:

- `LOG_LEVEL` - уровень логирования (debug, info, warn, error, fatal, panic)
- `GO_ENVIRONMENT` - окружение приложения (local, development, production)
- `WORKERS` - количество воркеров
- `LISTEN_HTTP` - адрес HTTP сервера (по умолчанию: `:8080`)

#### gRPC настройки:

- `GRPC_ADDR` - адрес gRPC сервера (по умолчанию: `:8090`)
- `GRPC_AUTH_IS_ENABLED` - включена ли аутентификация (по умолчанию: false)
- `GRPC_AUTH_HMAC_SECRET` - секрет для HMAC подписи токенов
- `GRPC_AUTH_JWT_REFRESH_SECRET` - секрет для refresh токенов
- `GRPC_AUTH_ACCESS_TOKEN_EXPIRY` - время жизни access токена (по умолчанию: 15m)
- `GRPC_AUTH_REFRESH_TOKEN_EXPIRY` - время жизни refresh токена (по умолчанию: 10080m = 7 дней)
- `GRPC_AUTH_MUST_VALIDATE_CLAIMS` - обязательная валидация claims (по умолчанию: false)
- `GRPC_USE_REFLECTION` - использование gRPC reflection (по умолчанию: false)

#### База данных:

- `POSTGRES_DSN` - строка подключения к PostgreSQL

#### RabbitMQ:

- `RABBITMQ_URI` - URI подключения к RabbitMQ
- `RABBITMQ_RECONNECT_RETRIES` - количество попыток переподключения (по умолчанию: 10)
- `RABBITMQ_RECONNECT_DELAY_SECONDS` - задержка между попытками (по умолчанию: 5)
- `RABBITMQ_GATES_LIST` - список гейтов для обработки сообщений
- `RABBITMQ_GATES_CONSUMER_COUNT` - количество консьюмеров для каждого гейта
- `RABBITMQ_TUNE_TOPOLOGY` - настройка топологии RabbitMQ (по умолчанию: false)

#### Трейсинг:

- `TRACER_ADDR` - адрес OpenTelemetry collector

#### Хранилище файлов (опционально):

- `STORAGE_ENABLED` - включить хранилище (по умолчанию: false)
- `STORAGE_PROVIDER` - тип хранилища: "s3" или "minio" (по умолчанию: minio)
- `STORAGE_ENDPOINT` - адрес хранилища
- `STORAGE_ACCESS_KEY_ID` - ключ доступа
- `STORAGE_SECRET_ACCESS_KEY` - секретный ключ
- `STORAGE_BUCKET_NAME` - имя бакета
- `STORAGE_USE_SSL` - использовать SSL (по умолчанию: false)
- `STORAGE_REGION` - регион для S3 (по умолчанию: us-east-1)

### Файлы конфигурации

- `config/config.go` - структура конфигурации
- `config/local.sample.env` - пример конфигурации
- `config/local.dev.env` - конфигурация для локальной разработки

## 9. Инфраструктура

### Docker Compose

Для локальной разработки используется Docker Compose с следующими сервисами:

- **postgres** - PostgreSQL 15.4
- **rabbitmq** - RabbitMQ 3-management-alpine
- **db-creator** - Создание базы данных при первом запуске
- **migrations** - Выполнение миграций БД
- **app** - Основное приложение

### CI/CD

Проект использует GitLab CI/CD для автоматизации сборки и деплоя:

#### Стадии пайплайна:

1. **build** - Сборка Docker образа приложения
2. **build-migrations** - Сборка Docker образа для миграций
3. **migrate** - Выполнение миграций базы данных
4. **deploy** - Деплой приложения

#### Registry

Docker образы хранятся в Harbor registry (`harbor.autocard-yug.ru`).

### Команды Makefile

- `make lint` - запуск линтера golangci-lint
- `make gen-envs` - генерация файла с переменными окружения
- `make vendor` - установка vendor зависимостей для protobuf
- `make generate-proto` - генерация кода из protobuf
- `make generate-api` - генерация API (protobuf + swagger)
- `make test-local` - запуск локальных тестов
- `make test-integration` - запуск интеграционных тестов
- `make generate-mocks` - генерация моков через mockery
- `make local-up` - запуск локального окружения через Docker Compose
- `make local-down` - остановка локального окружения
- `make local-logs` - просмотр логов

## 10. Разработка

### Требования

- Go 1.24.6
- Docker и Docker Compose
- Protocol Buffers compiler (protoc)
- Go инструменты для protobuf

### Локальный запуск

1. Клонировать репозиторий
2. Настроить переменные окружения (можно использовать `config/local.dev.env`)
3. Запустить через Docker Compose:
   ```bash
   make local-up
   ```
   или
   ```bash
   docker compose up --build
   ```

### Генерация кода

После изменения `.proto` файлов необходимо сгенерировать код:

```bash
make generate-api
```

Это команда:
1. Устанавливает vendor зависимости для protobuf
2. Генерирует Go код из protobuf
3. Генерирует gRPC клиенты и серверы
4. Генерирует HTTP gateway код
5. Генерирует Swagger документацию
6. Исправляет теги в Swagger через Python скрипт

### Тестирование

- **Локальные тесты:** `make test-local`
- **Интеграционные тесты:** `make test-integration`
- **Тесты в контейнере:** `make local-test`

### Линтинг

Линтинг выполняется через golangci-lint:

```bash
make lint
```

Конфигурация линтера находится в `.golangci.yml`.

### Моки

Моки генерируются через mockery. Конфигурация в `.mockery.yaml`:

```bash
make generate-mocks
```

## 12. Мониторинг и логирование

### Логирование

- Используется библиотека `alogger` для структурированного логирования
- Поддержка различных уровней логирования
- Интеграция с OpenTelemetry для трейсинга

### Метрики

- Prometheus метрики доступны на `/metrics`
- Метрики собираются через `ametrics` утилиту
- Метрики включают информацию о запросах, ошибках, производительности

### Трейсинг

- OpenTelemetry для распределенного трейсинга
- Интеграция с gRPC и HTTP middleware
- Отправка трейсов на указанный адрес collector

## 13. Интеграции

### RabbitMQ

Приложение интегрируется с другими сервисами через RabbitMQ:

- **Upstream Exchange** - для получения сообщений от других сервисов
- **Downstream Exchange** - для отправки сообщений другим сервисам
- Поддержка различных routing keys для разных типов сообщений
- Dead Letter Queue для обработки неудачных сообщений
- Настраиваемое количество консьюмеров для каждого гейта

### Типы сообщений:

- Документы (`docs`)
- Шаблоны (`templates`)
- Чеки (`receipts`)
- Миграция документооборота (`migrationDocflows`)
- Обновление контактов (`contactsUpdate`)
- Подтверждения пакетов (`acks`)
- Подтверждения шаблонов (`templateAcks`)
