# Система уведомлений

## Обзор

Система уведомлений состоит из четырех таблиц, которые позволяют отправлять и отслеживать push-уведомления через Firebase Cloud Messaging (FCM):

1. `fcm_tokens` - хранит токены пользователей для отправки уведомлений
2. `notification_types` - справочная таблица типов уведомлений
3. `notifications` - хранит сами уведомления, создаваемые серверной частью
4. `notification_user` - связывает уведомления с пользователями и отслеживает статус прочтения

## Таблицы

### 1. fcm_tokens

Таблица хранит токены Firebase Cloud Messaging для каждого пользователя. Фронтенд создает и удаляет токены при авторизации/деавторизации пользователя.

**Поля:**
- `id` - UUID, первичный ключ
- `user_id` - UUID, внешний ключ на таблицу users
- `token` - текст, токен FCM
- `created_at` - дата создания
- `updated_at` - дата обновления

### 2. notification_types

Справочная таблица типов уведомлений, которая определяет шаблоны и настройки для различных типов уведомлений.

**Поля:**
- `id` - UUID, первичный ключ
- `type` - текст, уникальный код типа уведомления
- `name` - текст, название типа уведомления
- `title` - текст, шаблон заголовка уведомления
- `body_template` - текст, шаблон текста уведомления
- `data_fields` - массив текста, поля, которые могут быть в data уведомления
- `is_user_configurable` - boolean, может ли пользователь настраивать получение этого типа уведомлений
- `created_at` - дата создания
- `updated_at` - дата обновления
- `deleted_at` - дата удаления (для мягкого удаления)

### 3. notifications

Таблица хранит уведомления, создаваемые серверной частью. Содержит заголовок, текст и дополнительные данные.

**Поля:**
- `id` - UUID, первичный ключ
- `title` - текст, заголовок уведомления
- `body` - текст, тело уведомления
- `data` - JSONB, дополнительные данные уведомления
- `notification_type_id` - UUID, внешний ключ на таблицу notification_types
- `created_at` - дата создания
- `updated_at` - дата обновления
- `deleted_at` - дата удаления (для мягкого удаления)

### 4. notification_user

Промежуточная таблица, которая связывает уведомления с пользователями и отслеживает статус прочтения.

**Поля:**
- `notification_id` - UUID, внешний ключ на таблицу notifications
- `user_id` - UUID, внешний ключ на таблицу users
- `is_read` - boolean, статус прочтения (по умолчанию FALSE)
- `created_at` - дата создания
- `updated_at` - дата обновления
- `deleted_at` - дата удаления (для мягкого удаления)

## Работа системы

### 1. Сохранение токена FCM

Когда пользователь авторизуется в приложении, фронтенд:
- Получает токен FCM от Firebase SDK
- Отправляет токен на сервер
- Сервер создает запись в таблице `fcm_tokens`

### 2. Создание уведомления

Когда серверу нужно отправить уведомление:
- Определяется тип уведомления (из справочника `notification_types`)
- Создается запись в таблице `notifications` с заголовком, телом и дополнительными данными
- Для каждого пользователя, которому нужно отправить уведомление, создается связь в таблице `notification_user`

### 3. Отправка push-уведомления

Сервер:
- Получает токены FCM для пользователей из таблицы `fcm_tokens`
- Получает тип уведомления из `notification_types`, чтобы определить, должен ли пользователь получать это уведомление (учитывая настройки)
- Отправляет уведомление через Firebase Cloud Messaging API
- Не отправляет уведомление, если у пользователя нет токена или если тип уведомления не требует push-уведомления

### 4. Отображение уведомлений пользователю

Фронтенд может:
- Запрашивать список уведомлений пользователя из таблицы `notification_user`
- Помечать конкретное уведомление как прочитанное, устанавливая `is_read = true`
- Помечать все непрочитанные уведомления как прочитанные

## Примеры использования

### Отправка уведомления конкретному пользователю:

```sql
-- Создать уведомление
INSERT INTO notifications (title, body, data, notification_type_id)
VALUES ('Новое сообщение', 'У вас новое сообщение от Ивана', '{"type": "message", "sender_id": "123"}',
        (SELECT id FROM notification_types WHERE type = 'custom'));

-- Связать с пользователем
INSERT INTO notification_user (notification_id, user_id)
VALUES ('[ID созданного уведомления]', '[ID пользователя]');
```

### Получение уведомлений пользователя:

```sql
SELECT n.title, n.body, n.data, nt.type, nu.is_read, nu.created_at
FROM notifications n
JOIN notification_user nu ON n.id = nu.notification_id
JOIN notification_types nt ON n.notification_type_id = nt.id
WHERE nu.user_id = '[ID пользователя]'
ORDER BY nu.created_at DESC;
```

### Пометка уведомления как прочитанного:

```sql
UPDATE notification_user
SET is_read = true, updated_at = now()
WHERE notification_id = '[ID уведомления]' AND user_id = '[ID пользователя]';
```

## Особенности

- Таблица `fcm_tokens` не использует мягкое удаление, так как это может привести к отправке уведомлений несуществующим пользователям
- При удалении пользователя все связанные токены FCM автоматически удаляются (CASCADE)
- При удалении уведомления все связи с пользователями также удаляются (CASCADE)
- Статус прочтения уведомления отслеживается индивидуально для каждого пользователя
- Таблица `notification_types` позволяет систематизировать все типы уведомлений и определить, какие из них могут быть отключены пользователем
